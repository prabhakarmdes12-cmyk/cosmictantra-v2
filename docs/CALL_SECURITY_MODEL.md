## 1. Cryptographic Reality & Encryption Truth

### 1.1 The Marketing Claim vs. The Technical Architecture
Previous UI mockups in the repository claimed:
> *"🔒 256-Bit DTLS-SRTP End-to-End Encrypted Room initialized. Real phone numbers are masked on both ends."*

This statement requires precise technical qualification:

```
[Browser A: Devotee]                                          [Browser B: Consultant]
        │                                                               │
        │◀═════════════════════ WSS Signaling (TLS 1.3) ════════════════▶│
        │                        (Session Setup Only)                   │
        │                                                               │
        │◀─────────────────── ICE Candidate Exchange ──────────────────▶│
        │                                                               │
        │◀═══════════════════ DTLS 1.2 / 1.3 Handshake ════════════════▶│
        │               (ECDHE-ECDSA-AES-128/256-GCM)                   │
        │                                                               │
        │████████████████████ SRTP Audio / Video Stream ████████████████▶│
        │               (Encrypted with DTLS-derived keys)              │
```

### 1.2 Media Encryption (DTLS-SRTP)
Under RFC 8826 and RFC 8827, **WebRTC mandates media encryption**:
1. All audio (Opus) and video (VP8/H.264) RTP packets are encrypted using **SRTP (Secure Real-time Transport Protocol)** with **AES-GCM (128-bit or 256-bit)** or **AES-CTR** with HMAC-SHA1.
2. The encryption keys for SRTP are **never sent over the signaling server**. They are negotiated directly between the two browser endpoints over the media path using **DTLS (Datagram Transport Layer Security)** with ephemeral Diffie-Hellman keys (`ECDHE`).
3. An intermediary signaling server (even CosmicTantra's own servers) only sees the SDP fingerprints (SHA-256 hashes of the self-signed X.509 certs generated by each browser). The server **cannot decrypt the media stream**.

### 1.3 Distinguishing P2P Transport Security from SFU E2EE
- **In Peer-to-Peer (1:1 WebRTC)**: The connection between the Devotee and Consultant is **True End-to-End Encrypted**. No server or third party receives or decodes the unencrypted RTP packets.
- **In TURN Relay Mode**: The TURN server (STUN/TURN RFC 5766) relays UDP/TCP packets at the network transport layer. The TURN server **cannot see or decrypt media** because SRTP encryption occurs inside the payload prior to TURN encapsulation.
- **In SFU/Media Server Mode (e.g. LiveKit / Mediasoup)**: If a media server is introduced in future multi-party calls, standard WebRTC decrypts media at the SFU to re-packetize it unless **WebRTC Insertable Streams (SFrame / MLS)** are configured. 
- **Rule for CosmicTantra V1**: V1 is strictly **1:1 Peer-to-Peer**. Therefore, **media is genuinely End-to-End Encrypted between Devotee and Consultant**.

## 2. Signaling Security & Ephemeral Access Model

### 2.1 Transport Security (HTTPS & WSS)
- All WebRTC signaling (offers, answers, ICE candidates) must traverse **TLS 1.3 WebSockets (`wss://`) or authenticated SSE/HTTPS**.
- Unencrypted HTTP (`ws://`) is strictly prohibited in production. WebRTC APIs (`getUserMedia`, `RTCPeerConnection`) are sandboxed by browser security policies and **refuse to execute on non-secure origins**.

### 2.2 Unpredictable Room IDs
Room IDs must never be predictable integers (`/room/1`, `/room/1432`).
- Room identifiers are generated cryptographically using high-entropy random identifiers:
  $$\text{Room ID} = \text{UUIDv4} \quad \text{or} \quad \text{nanoid}(24, \text{'0123456789abcdefghijklmnopqrstuvwxyz'})$$
- Example: `ct-room-9f8a3c2e-4b11-49fa-802d-780c7a52f41d`
- Brute-force discovery probability: $< 10^{-20}$, eliminating room enumeration attacks.

### 2.3 Ephemeral Cryptographic Session Authorization (HMAC-SHA256)
A user cannot join a room simply by knowing or guessing the URL. Access requires an **ephemeral cryptographic consultation token** issued by `src/lib/sabha/auth.ts`:

```typescript
interface SabhaAccessToken {
  sessionId: string;
  roomId: string;
  userId: string;
  role: 'CUSTOMER' | 'CONSULTANT' | 'OPS';
  issuedAt: number;     // Unix timestamp (ms)
  expiresAt: number;    // Exactly 45 minutes from issuance
  signature: string;    // HMAC-SHA256(payload, process.env.SABHA_SECRET)
}
```

**Enforcement Rules**:
1. When a client connects to the signaling server, it presents `token`.
2. The server verifies the HMAC signature using constant-time comparison (`crypto.timingSafeEqual`).
3. If `expiresAt < Date.now()`, the connection is immediately terminated with error code `AUTH_TOKEN_EXPIRED`.
4. The server validates that the `roomId` matches the token's authorized room.
5. Exactly **two peers** (`1 CUSTOMER` + `1 CONSULTANT`) are permitted inside a consultation room. A third connection attempt is immediately rejected with `ROOM_CAPACITY_EXCEEDED`.

## 3. Privacy Policy & PII Protection

### 3.1 Zero Phone Number Disclosure Invariant
- **Fundamental Invariant**: Under no circumstance is a devotee's or consultant's personal phone number, WhatsApp ID, or email address displayed or transmitted over client-accessible channels.
- **Client Identity Masking**:
  - Devotee sees Consultant as: `"पंडित विद्यानंद शास्त्री (वाराणसी)"` (Verified Scholar Badge).
  - Consultant sees Devotee as: `"Devotee #CT-8492 (रोहिणी नक्षत्र, वृषभ लग्न)"` or First Name only (`"राहुल"`).
- In the event of network failure requiring PSTN fallback (`telephonyHandover.ts`), the call is bridged via Exotel Virtual Masked DIDs. Neither party's device displays the other's true caller ID.

### 3.2 IP Address Exposure Mitigation (P2P vs. TURN Relay)
In standard WebRTC peer-to-peer mode, direct peer connectivity requires exchanging host IP addresses via ICE candidates. In adversarial situations, a rogue peer could discover the other peer's public IP address.

**CosmicTantra Mitigation Strategy**:
1. **ICE Candidate Filtering**:
   - For high-privacy sessions, the signaling server can instruct the WebRTC client to use `iceTransportPolicy: 'relay'`.
   - In relay mode, only TURN server relay IP addresses are exchanged, completely masking the devotee's and consultant's home/mobile IP addresses from each other.
2. **Default V1 Posture**:
   - Host and reflexive candidates are permitted for minimal latency, but clients are given the option for `"Strict Masked Connection"` (forcing TURN relay) if enhanced privacy is required.

## 4. Strict Zero-Recording & Data Retention Policy

### 4.1 Zero Media Recording Invariant (`VOICE_INV_007`)
- **CosmicTantra enforces a strict ZERO-RECORDING policy for audio and video media.**
- There are **no recording microservices**, **no RTP packet dump utilities**, **no storage buckets (S3/GCS)**, and **no browser `MediaRecorder` instances** attached to consultation streams.
- Audio and video streams exist purely in volatile memory inside browser hardware buffers during the live conversation and are immediately destroyed upon call termination (`pc.close()`, track stop).

### 4.2 Operational Metadata Retention (The Minimal Audit Trail)
Only operational metadata necessary for system reliability, dispute resolution, and billing audit is retained:
- `sessionId` (UUID)
- `customerId` / `guestId` (Pseudonymous identifier)
- `consultantId` (Verified scholar ID)
- `assignedBy` (Operator ID)
- `status` (`COMPLETED`, `DECLINED`, `FAILED`, `TIMEOUT`)
- `createdAt`, `connectedAt`, `endedAt` (Server timestamps)
- `durationSeconds` (Authoritative connected time)
- `telemetry`: Round-trip time (RTT), jitter (ms), packet loss (%), ICE candidate type (`host` / `srflx` / `relay`).
- **Forbidden from storage**: Voice audio, video frames, conversational speech-to-text transcripts, and caller caller-ID strings.

## 5. TURN Server Security & Ephemeral Credential Lifecycle

### 5.1 Why TURN is Mandatory for India Network Reality
In India, over 75% of mobile internet users (Jio, Airtel, Vi) operate behind **Carrier-Grade NAT (CGNAT / Symmetric NAT)** with strict firewall filtering. Direct STUN peer-to-peer hole-punching fails in 20%–35% of cross-network sessions (e.g. Jio 5G to BSNL broadband). Without a TURN relay, one in three calls will fail silently in the `CONNECTING` state.

### 5.2 Ephemeral TURN Credentials (RFC 5766 REST API)
Permanent static TURN passwords embedded in frontend JavaScript are a severe vulnerability: third parties can steal credentials and use the TURN server as a free global bandwidth proxy.

**CosmicTantra Ephemeral Credential Generation Protocol**:
1. When a client enters a room, it requests TURN credentials from `GET /api/rtc/turn-credentials`.
2. The server verifies session authorization and generates a time-limited HMAC credential valid for **30 minutes**:
   $$\text{Username} = (\text{Current Timestamp} + 1800) : \text{userId}$$
   $$\text{Password} = \text{Base64}(\text{HMAC-SHA1}(\text{Username}, \text{TURN\_SECRET}))$$
3. The coturn server verifies this credential independently using the shared secret without needing a database lookup.
4. When the 30-minute window expires, the coturn server rejects new allocations, preventing bandwidth theft.

## 6. Threat Model & Countermeasure Matrix

| Threat Actor | Attack Vector | Potential Impact | CosmicTantra Technical Countermeasure |
|---|---|---|---|
| **Eavesdropper on Public Wi-Fi** | Packet sniffing on unencrypted LAN | Intercept audio/video | **DTLS-SRTP** encrypts all RTP packets. Eavesdropper sees only high-entropy UDP ciphertext. |
| **Rogue Stranger / Web Crawler** | Room enumeration & URL guessing | Join private consultation | **Cryptographic UUIDv4 room IDs** ($2^{122}$ entropy) + Ephemeral HMAC session tokens required on signaling handshake. |
| **Malicious Devotee / Stalker** | Harvesting Pandit's private phone number | Harassment, off-platform solicitation | **Zero PII exposure**: WebRTC transmits only media packets over internal ports; phone numbers never touch the frontend. |
| **Attacker probing IP address** | Reading WebRTC SDP ICE candidates | Locating devotee or scholar physical city/ISP | Configurable **TURN Relay Only mode (`iceTransportPolicy: 'relay'`)** masks client IP behind relay server IP. |
| **Bandwidth Leech** | Stealing TURN credentials for personal torrent/VPN | Skyrocketing bandwidth bills | **Ephemeral REST credentials (RFC 5766)** with 30-minute TTL tied to authenticated session ID. |
| **Compromised Signaling Server** | Inspecting signaling messages | Eavesdropping on media | Signaling server handles only SDP descriptions and ICE candidates; it **does not possess DTLS private keys** and cannot decrypt SRTP media. |
| **Disgruntled Operator** | Wiretapping ongoing call | Privacy breach | Operator assigns and routes, but **does not join the WebRTC media room**. Room capacity is strictly hardcoded to 2 participants. |
